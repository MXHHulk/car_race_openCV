循跡自走車系統架構

從鏡頭取像、在 Orin 上辨識黑底白線，到透過 UART 下指令給 BMduino 驅動舵機與馬達，讓車子不靠電腦、不靠網路自己跑完賽道。

總覽硬體與資料流鏡頭接收YOLO 與 OpenCV 辨識流程控制下指令BMduino 離線執行安全程式結構開發順序待決定事項

00總覽

整台車分成五層，每一層只做一件事，並且只把結果交給下一層：

  1. 取像：USB 鏡頭持續拍照，只保留最新的一張。
  2. 辨識：用 OpenCV 找出左右兩條白線，算出「車子偏離中線多少、車頭歪了多少、前方彎多急」。
  3. 控制：把上面三個數字換算成前輪轉角 fwa 和後輪速度 bwl、bwr。
  4. 通訊：每 50 ms 把最新的指令包成 CMD 封包，從 UART 送給 BMduino。
  5. 執行：BMduino 解析指令，透過 PCA9685 轉舵機、透過驅動板轉馬達，並負責失聯時停車。

01硬體與資料流

連線介面內容現況
鏡頭 → OrinUSB（UVC / V4L2）MJPG 640×480，30 fps可用 cam_stream.py 已測過
Orin ↔ BMduinoUART /dev/ttyTHS1，115200 8N1CMD 往下送、STA 往上回，XOR8 checksum已通過 99/99 封包有效
BMduino → PCA9685I2C，位址 0x40CH0 舵機（50 Hz 脈寬）、CH1~CH4 驅動板 IN1~IN4待確認 舵機還沒測
BMduino → 驅動板D8、D9 → 74LS14 → ENA、ENBPWM 調速有問題 馬達 A 不轉、IN3 無作用
編碼器 → BMduinoD4~D7兩顆馬達的 A/B 相未使用 之後做定速控制用

每一段花多少時間

從「畫面裡的線歪了」到「輪子開始轉向」，中間每一段都會延遲。延遲越長，車子越容易左右搖擺，所以速度上限主要由這張表決定：

階段預估時間說明
鏡頭曝光與傳輸33–66 ms30 fps 時一張約 33 ms，USB 鏡頭內部通常還有 1 張緩衝
OpenCV 辨識5–15 ms320×240 灰階影像，估計值，實測後再更新
等待下一次送出0–50 ms指令固定 20 Hz 送出；之後可以改成辨識完立刻送
UART 傳輸≈ 2.3 ms26 byte × 10 bit ÷ 115200
舵機轉到定位50–150 ms依舵機規格，通常是最慢的一段

合計大約 0.1 到 0.3 秒。車速每秒 1 公尺時，這段時間車子會往前走 10 到 30 公分，所以控制要「看遠一點」（見第 05 節）。

02鏡頭接收

做法

  • 用 OpenCV 的 VideoCapture(0, CAP_V4L2) 開啟 USB 鏡頭，格式設成 MJPG 640×480。這和現有的 cam_stream.py 相同，可以直接沿用。
  • 獨立執行緒一直讀取，只保留最新的一張，舊的直接丟掉。辨識拿到的永遠是最新畫面，不會因為處理比較慢而越積越多、越來越延遲。
  • 每一張影像都記下取得的時間，用來計算延遲和找不到線的時間。
  • 辨識前先縮成 320×240。白線很粗，解析度降低不影響判斷，速度卻快很多。

鏡頭設定（很重要）

自動曝光和自動白平衡會讓同一條白線在不同位置亮度不同，二值化的結果就會跳動。建議用 v4l2-ctl 把它們關掉，改成固定值：

v4l2-ctl -d /dev/video0 --list-ctrls            # 先看這顆鏡頭支援哪些設定
v4l2-ctl -d /dev/video0 -c auto_exposure=1       # 手動曝光（實際名稱依鏡頭而定）
v4l2-ctl -d /dev/video0 -c exposure_time_absolute=150

安裝位置

  • 鏡頭越高、越往前，看得越遠，但近處會有盲區。建議先讓畫面下緣剛好看到車頭前方 10 到 20 公分。
  • 位置和角度一旦固定就不要再動。鳥瞰轉換的校正，以及所有錄下來的測試影片，都和這個位置綁在一起。

03YOLO 和 OpenCV 差在哪

這兩個不是二選一的關係，它們擅長的事情不一樣：

傳統 OpenCVYOLO 物件偵測語意分割（YOLO-seg、U-Net）端到端模型
原理用規則處理像素：門檻、邊緣、幾何擬合神經網路框出「物體」的位置（矩形框）神經網路判斷每個像素是不是線神經網路直接從畫面輸出轉角
需要標註資料不用要，通常數百張以上要，而且要畫像素等級的遮罩要，人工開車錄下大量資料
在 Orin Nano 上CPU 就很快，每張幾毫秒需要 TensorRT 加速才能即時比偵測更吃 GPU視模型大小而定
適合找細長的線嗎很適合不適合，細長斜線用矩形框框不準適合間接學到
出錯時好不好查好查，每一步都能看中間結果難，要補資料重新訓練難非常難
適合用在對比強烈的黑底白線交通標誌、障礙物、角錐、紅綠燈光線複雜、線段斷斷續續的場地研究用，不建議當主要方法

建議：用 OpenCV 找線，YOLO 只在比賽有物件要辨識時才加。

黑底白線的對比非常強，用門檻就能把線分出來，不需要訓練模型，出錯時也能一步一步看是哪裡錯。如果賽道上還有標誌、障礙物或紅綠燈，再另外加一個 YOLO（例如 YOLOv8n 或 YOLO11n，轉成 TensorRT），讓它和找線並行，結果交給狀態機決定要減速、停車還是避開。

04OpenCV 辨識流程

每一張畫面依序經過下面七步，最後輸出四個數字給控制層。

步驟做什麼OpenCV 函式要調的參數
1. 裁切 ROI只保留畫面下半部（路面）陣列切片保留比例，約 50–60%
2. 灰階 + 模糊去掉顏色和雜訊cvtColor、GaussianBlur模糊核心 5×5
3. 二值化白線變白、黑底變黑threshold（Otsu）反光嚴重時改用固定門檻或 adaptiveThreshold
4. 去雜點去掉小白點、補小缺口morphologyEx（開運算）核心 3×3
5. 鳥瞰轉換把透視畫面拉成俯視，兩條線變平行getPerspectiveTransform、warpPerspective四個校正點（只做一次）
6. 找線直方圖找兩條線的起點，再用滑動視窗往上追numpy 運算視窗數 9、寬度、最少像素數
7. 擬合左右線各擬合成二次曲線 x = ay² + by + cnp.polyfit無

輸出給控制層的四個值

名稱意義單位
offset車子中心偏離道路中線多少，正值代表車子偏右公分（由校正得到每像素幾公分）
heading車頭方向和道路方向的夾角度
curvature前方的彎有多急1/公尺
confidence這一張畫面的結果可不可信：兩條線都有 = 1、只有一條 = 0.5、都沒有 = 00–1

會出錯的情況，以及怎麼處理

  • 轉彎時只看得到一條線：用已知的道路寬度，從看得到的那條線往旁邊推半個路寬，當作中線。
  • 反光被誤認成線：檢查兩條線的距離是否接近道路寬度、是否大致平行。不合理就丟掉這一張，沿用上一張的結果。
  • 結果每張都跳來跳去：對擬合係數做移動平均，讓結果平滑。
  • 速度優化：上一張已經找到線，下一張就只在那條線附近搜尋，不用每次重新跑滑動視窗。

鳥瞰轉換的校正方式

  1. 車子停在直線賽道正中央，鏡頭裝在最終位置。
  2. 拍一張照片，在兩條白線上各點兩個點（近處一個、遠處一個），共四點。
  3. 指定這四點在俯視圖中應該形成一個矩形，存進 config.yaml。
  4. 同時量好實際的道路寬度和那段距離，就能得到「每像素幾公分」。

05控制：從辨識結果到轉角和速度

轉向：兩種方法

PD 控制Pure Pursuit（建議）
公式fwa = Kp·offset + Kd·Δoffset/Δt + Kh·heading在中線上找前方 Ld 公分的目標點，夾角為 α：
fwa = atan(2·L·sin α / Ld)，L 為前後輪軸距
要調的參數Kp、Kd、Kh 三個主要只有 Ld（看多遠）
優點簡單、好理解天生「看遠一點」，能彌補第 01 節的延遲；參數有物理意義
缺點參數彼此影響，延遲大時容易搖擺需要量軸距，也需要鳥瞰轉換換算出實際距離

Ld 調整原則：太小會左右搖擺，太大過彎會切內線。可以從 1.5 倍車長開始試，速度越快就看越遠。

速度規劃

  • 彎越急、越慢：v = v_max × (1 − k·|curvature|)，並設定最低速度。
  • 辨識結果不可信時減速：v = v × confidence。
  • 後輪差速（選用）：轉彎時內輪比外輪慢，v_內 = v·(1 − W/2R)、v_外 = v·(1 + W/2R)，W 是兩後輪的距離、R 是轉彎半徑。只有一顆馬達出力時可以先不做。

狀態機

stateDiagram-v2
  state "待命" as idle
  state "行駛" as run
  state "找不到線" as lost
  state "停止" as halt
  [*] --> idle
  idle --> run: 按下出發鈕
  run --> lost: confidence = 0
  lost --> run: 0.3 秒內重新找到
  lost --> halt: 超過 0.3 秒
  run --> halt: 終點線 / 再按一次按鈕
  halt --> idle: 按下按鈕

「找不到線」的這 0.3 秒內，維持最後一次的轉角並減速，讓車子有機會在彎道重新抓回線。

06下指令給 BMduino

沿用 motor_cmd.py 裡的 BMduinoLink，格式完全依照《UART 通訊協議書》：

<CMD,fwa 12,bwl 35,bwr 40,cs XX>\n
  fwa  前輪轉角  -90 ~ 90 度（負左正右）
  bwl  左後輪    -100 ~ 100 %（正前進）
  bwr  右後輪    -100 ~ 100 %
  cs   XOR8 checksum，兩位大寫十六進位
  • 獨立的送指令執行緒：每 50 ms 送一次「目前最新」的指令，和辨識花多少時間無關。這樣辨識偶爾變慢時，BMduino 也不會誤判成失聯。
  • 送出前先限制範圍，轉角也受機構上限限制（目前設 ±30 度）。
  • 同一個執行緒負責讀 STA。超過 0.5 秒沒收到 STA，就讓主程式進入「停止」狀態，並在除錯畫面顯示警告。
  • 程式結束、出錯、被 Ctrl+C 中斷時，一律先送 3 次 fwa 0,bwl 0,bwr 0 再關閉序列埠。
  • 之後如果要降低延遲，可以把鮑率提高到 460800（協議書有列出這個選項），兩邊都要同時改。

07BMduino：把指令變成馬達動作

韌體 bmduino_motor.ino 已經寫好，主迴圈做這幾件事：

  1. 收封包：以 < 和 > 切出完整封包，驗證 checksum、三個欄位都要有、數值要在範圍內，不合格的整包丟掉。
  2. 舵機：PCA9685 CH0 輸出 50 Hz 脈寬。1500 µs 是正中間，每度約 11 µs，可以用 SERVO_CENTER_US 修正置中。
  3. 馬達：IN 腳決定方向（PCA9685 CH1~CH4），EN 腳用 PWM 決定力道（D8、D9）。換方向前先把 EN 關掉。
  4. 失聯保護：超過 500 ms 沒收到有效 CMD 就讓兩顆馬達停止，舵機維持最後角度。
  5. 回報：每 100 ms 回一次 STA。

之後要加的：編碼器定速控制

現在 bwl 40 代表「給馬達 40% 的力道」，實際速度會隨電池電量和坡度改變。加上編碼器之後，可以改成「維持最高轉速的 40%」：

  • 用中斷計數 D4~D7 的脈衝，每 10 ms 算一次轉速。
  • 用 PI 控制調整 EN 的 PWM，讓實際轉速追上目標轉速。
  • STA 加上兩個欄位回報實際轉速，例如 <STA,S1 -1,vl 38,vr 41,cs XX>。新增欄位前要先和組員約定。

目前卡住的地方：診斷結果只有 B2 步驟會轉，代表馬達 A 那一路和 IN3 有硬體問題。這個要先解決，第 05 節的控制才有辦法在實車上調整。

08離線執行：不靠電腦、不靠網路

  • 所有程式都在 Orin 本機上跑，不需要網路。SSH 只在開發時使用。
  • 把主程式設成 systemd 服務，Orin 開機就會自動啟動，進入「待命」狀態： 
    [Unit]
Description=Lane follower
After=multi-user.target

[Service]
User=jetson
WorkingDirectory=/home/jetson/orin_tools/lane
ExecStart=/usr/bin/python3 main.py
Restart=on-failure

[Install]
WantedBy=multi-user.target
  • 實體出發鈕：接一顆按鈕到 BMduino（或 Orin 的 GPIO）。按下就出發，再按一次就停。比賽現場不需要打開電腦。
  • 紀錄檔：每次行駛時，把每一張畫面的 offset、fwa、速度、confidence 寫進 CSV，跑完後再拿回電腦分析，也可以順便錄下影片。

09三層安全保護

層級觸發條件動作
Orin 辨識層超過 0.3 秒找不到線狀態機進入「停止」，送出速度 0
Orin 通訊層超過 0.5 秒沒收到 STA，或程式例外結束送出停車指令並停止
BMduino超過 0.5 秒沒收到有效 CMD（Orin 當機、線鬆脫）兩顆馬達停止

另外建議在電池和驅動板之間加一個實體電源開關，作為最後一道保護。

11開發順序

P0

修好馬達

完成杜邦線直接接驅動板的測試和 PCA9685 通道掃描，找出馬達 A 和 IN3 的問題。

完成標準：motor_cmd.py 能讓兩輪正轉、反轉，前輪能左右轉。

P1

固定鏡頭、錄素材

把鏡頭裝到最終位置，關掉自動曝光，推著車沿賽道錄影，直道、各種彎道都要錄到。再拍一張校正用的照片。

完成標準：有一段完整賽道的影片，以及鳥瞰校正參數。

P2

離線辨識

在電腦上用 replay.py 反覆調整 vision.py，直到整段影片都穩定抓到線。這個階段不需要實車。

完成標準：confidence 為 0 的畫面低於 2%，疊加的中線不會跳動。

P3

架高測試閉迴路

車子架高，用手拿一張印有白線的黑紙在鏡頭前移動，看前輪是否往正確方向轉，同時確認三層安全保護都有作用。

完成標準：轉向方向正確；拔掉 UART 線，輪子會在 0.5 秒內停止。

P4

實車低速

速度 20% 左右，先跑直線，再跑緩彎，最後跑急彎。主要調整 Ld。

完成標準：低速能跑完整圈，不需要人介入。

P5

提高速度

加上編碼器定速控制和速度規劃，逐步提高 v_max，並用紀錄檔分析在哪裡偏離最多。

完成標準：以目標速度連續跑 5 圈不出界。

P6

比賽準備

設定開機自動啟動和實體按鈕，關閉除錯串流，在比賽場地的燈光下重新確認二值化門檻。

完成標準：不接任何電腦，從開機到跑完賽道全部能自己完成。

  • 終點怎麼判斷：是橫向的白線、跑固定圈數，還是由人工按停？
  • 道路寬度、白線寬度、最小轉彎半徑：要實際量，會寫進 config.yaml。
  • 車子尺寸：前後輪軸距 L、兩後輪距離 W（Pure Pursuit 和差速會用到）。
  • D8、D9 是否支援 PWM：如果不支援，改由 PCA9685 對 IN 腳輸出 PWM 來調速（韌體要改寫）。
  • 舵機實際可轉的角度：決定 FWA_LIMIT。
